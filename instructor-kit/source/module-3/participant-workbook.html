3.1

An Interactive Animated Story

28 min
By the end you can
  • Add sprites and a backdrop from the libraries
  • Place sprites with go to and move them smoothly with glide
  • Make characters take turns with broadcast and when I receive
Key ideas
  • The stage is a grid: x is left–right (−240 to 240), y is down–up (−180 to 180), and the centre is 0, 0. Drag a sprite and read its x/y under the stage.
  • go to x: y: teleports (good for a starting spot). glide _ secs to x: y: slides (good for entrances).
  • Sprites can't see each other's scripts. A broadcast is an invisible signal that any sprite can send and any sprite can listen for, like a stage director calling a cue.
  • Only the first line starts with when ⚑ clicked. Every later line starts with when I receive.
Worked example
when ⚑ clicked
go to x: -200 y: -100
glide 2 secs to x: 0 y: -100
say Hi Bear! for 2 seconds
broadcast your turn
when I receive your turn
say Hi Cat! Nice day! for 2 seconds

Left: the Cat's script (sends the cue). Right: the Bear's script (listens for it). Both gold blocks are in Events. Choose New message the first time and give the cue a clear name.

Your turn — A Conversation That Plays Itself
  1. New project. Choose a Backdrop (bottom-right) and pick a setting. Choose a Sprite and add a second character.
  2. Cat (when ⚑ clicked): say a line, then broadcast [line 2].
  3. Other character (when I receive [line 2]): reply, then broadcast [line 3].
  4. Cat (when I receive [line 3]): reply, then broadcast [line 4].
  5. Both (when I receive [line 4]): say goodbye and glide off together.
  6. Bonus: click the Stage and give it when I receive [night] → switch backdrop to a night scene. Have a character broadcast "night."

3.2

A Simple Game with Variables & Score

32 min
By the end you can
  • Explain what a variable is and make one
  • Keep score with set and change, and show it on the stage
  • Combine loops, if, sensing, and operators into a real game
Key ideas
  • A variable is a labeled box (or a whiteboard) that holds a value the program can remember and change: a score, lives, a name.
  • Make a Variable is in the orange Variables category. Name it score and keep For all sprites. Tick its checkbox to show it live on the stage.
  • set [score] to 0 replaces the value. change [score] by 1 adds to it. The round (score) reporter reads it.
  • Reset the score once, right after the green flag, before the game loop.
  • Why check y position < -170 instead of touching edge? The apple starts at y: 170, where it's already touching the top edge, so "touching edge" would send it back to the top every frame and it would never fall.
Worked example
when ⚑ clicked
set score to 0
forever
go to x: pick random -200 to 200 y: 170
repeat until touching Cat?
change y by -8
if y position < -170 then
go to x: pick random -200 to 200 y: 170
change score by 1
when ⚑ clicked
forever
go to x: mouse x y: -140

Left: the Apple. Start at the top at a random x, fall until caught (jump back to the top if it drops past the bottom), then add a point, forever. Right: the Cat follows the mouse left–right along the bottom. Green = Operators, blue-green = Sensing. The bottom check puts the y position reporter (bottom of Motion) inside the green < block.

Your turn — Catch the Apple
  1. Add an Apple sprite (keep the Cat). Make the score variable and tick its checkbox.
  2. Build the Apple script. Watch the white landing shadow so each block drops into the right C-shaped mouth.
  3. Build the Cat script. mouse x is a round Sensing block that you drop into the x slot.
  4. Press the green flag and play. Then save: File → Save to your computer. You'll need it again.
  5. Challenge: a time left variable set to 30 that counts down by 1 each second, then broadcast [game over] and stop all.
Teach-It practice — Design first, code second

The one-page game design: Goal (catch apples) · Controls (move the mouse) · Scoring (+1 per catch) · Lose condition (timer runs out). Explain variables with a sticky note that says "SCORE: 0" and cross it out each time.

Before we code, tell me your game like you're explaining it to a friend. How do you play? How do you win? Let's write those down. Those are our to-do list.
Let's put that on the "someday" list and make catching one thing perfect first.

Role-play reflection: How did you steer the "child's" huge idea down to one mechanic without saying "no"?

3.3

Debugging & Remixing

30 min
By the end you can
  • Find and fix bugs with the 4-step method
  • Recognize the most common Scratch bugs
  • Use See Inside and explain good remixing etiquette
  • Coach a frustrated child without grabbing the mouse
Key ideas
  • A bug just means "not doing what I expected yet." The computer does exactly what the blocks say. Debugging is finding the gap between what you said and what you meant.
  • The 4-step loop: 1 Watch what actually happens → 2 Predict which block causes it → 3 Change ONE thing → 4 Test. Still wrong? Go round again.
  • Scratch's helpers: click one block to run just that piece, tick a variable's checkbox to watch it, add a temporary say (score), slow things down with wait.
  • See Inside opens any shared project's code. Remix (when signed in) makes your own copy. Scratch credits the original creator automatically. Change something meaningful and keep the credit.
Worked example — the usual suspects
SymptomUsual causeFix
Nothing happensCode is on the wrong spriteSelect the right sprite in the sprite list
Runs once, never reacts againAn if with no loop around itWrap the check in a forever
Blocks after a loop never runTrapped below a foreverMove them inside, or use repeat until
Sprite zooms off / upside-downPosition not reset / rotation styleAdd go to x/y at start; set rotation style to left-right
Score jumps by many at onceCondition stays true for many framesMove the sprite away, or add a short wait after scoring
Two sprites out of syncRelying on wait timingCoordinate with broadcast / when I receive

Your turn — The Bug Hunt (debugging buddies)

Teach-It practice — Coaching through frustration

Rubber duck: have the child explain the code block by block, to you or a stuffed animal. Ask, don't fix: use the navigator's four questions. Know when to break: walking away is a real debugging strategy, not quitting.

Walk me through it like I know nothing. What should this block do? …And what did it actually do?
The code has a bug; you're a coder who's finding it.
Let's let our brains rest. Coders do this all the time.
