Module 3 — Building Real Projects

How to run the session where parents stop following steps and start building things their kids will want to show off: a two-character animated story, a real catch game with a score, and a calm method for fixing bugs, practised on a game full of planted bugs.

3 lessons 2 hrs in class Lessons 3.1–3.3 Level Beginner Maps to Session S3

How to Use This Guide

  • Same rhythm for every lesson: Frame → Demo → Lab → Teach-It role-play → Check. The run-sheet below is the clock; the lesson blocks are the content.
  • This is the busiest session. Three lessons fit into two hours only if you demo tight and send people to the labs quickly. The reference .sb3 files in labs/module-3/ are your safety net. A participant who falls behind on 3.2 loads the finished game and still does the Bug Hunt.
  • The emotional arc matters. 3.1 feels delightful, 3.2 feels hard (say so out loud: "this one is a step up"), and 3.3 turns that difficulty into a skill. Parents who struggled in 3.2 often shine in the Bug Hunt.
  • 3-Saturday format: this session is the morning block of Saturday 2 (S4 follows after lunch). Keep the same timings.
  • Teal = hands-on, amber = watch-outs, dashed boxes = lines to say out loud.
The through-line

Three projects, one arc: make it → make it a game → make it work. The story (3.1) teaches sprites to cooperate with broadcasts. The catch game (3.2) adds a variable and combines every block category so far. The Bug Hunt (3.3) hands back that same game with four planted bugs, so participants debug code they already understand. The Teach-It thread matches it: story before code, design before code, ask, don't fix.

Before the Session

  • Copy labs/module-3/ to every machine (or a shared drive / USB): l3-1-conversation.sb3, l3-2-catch-the-apple.sb3, l3-3-bug-hunt-starter.sb3. Test loading one with File → Load from your computer.
  • Print the three kid cards (in each lesson block below) and one 4-step debugging card per pair (Watch → Predict → Change ONE thing → Test).
  • Bring mice, a few sticky notes (for the "SCORE" whiteboard demo in 3.2), and a stuffed animal for the rubber-duck demo in 3.3. It gets a laugh and people remember it.
  • Pair people up in advance: the Bug Hunt runs in debugging-buddy pairs. Mix confident and cautious participants.

If you run long

Protect the Bug Hunt. Cut in this order: (1) skip the 3.1 backdrop-change challenge, (2) shorten the 3.2 lab by letting slower pairs load l3-2-catch-the-apple.sb3 and just play it, (3) demo See Inside for 1 minute instead of 3. Never cut the wrap-up journal. It's how adults consolidate.

Lesson Plans

3.1

An Interactive Animated Story

28 min
Objectives
  • Add multiple sprites and a backdrop from the libraries
  • Position sprites with go to x: y: and glide _ secs to x: y:
  • Coordinate sprites with broadcast and when I receive
  • Coach a child to plan the story out loud before coding it
Teaching sequence
  1. Set the scene (2m). New project → Choose a Backdrop (bottom-right, under the stage) → "Forest." Choose a Sprite → add a Bear. Remind them: click the sprite first, then add blocks.
  2. The grid, teleport vs slide (4m). Stage is x −240…240, y −180…180, centre 0,0. Build the entrance script live:
    when ⚑ clicked
    go to x: -200 y: -100
    glide 2 secs to x: 0 y: -100
    say Hello, forest! for 2 seconds
    Watch the numbers under the stage change as I drag the cat. That's where x and y come from. You never have to guess them.
  3. The problem broadcasts solve (6m). Ask the room: "How does the Bear know the Cat has finished talking?" Let them suggest wait blocks, then point out that the timing drifts. Act it out: you are the stage director, two volunteers are Cat and Bear. Say "Cue: your turn!" and the Bear answers. Then build it: Cat gets broadcast [your turn] (choose New message and name it), Bear gets when I receive [your turn].
    A broadcast is an invisible shout. Any sprite can shout it, and any sprite that's listening springs into action.
  4. Lab launch (0m, just go). Show the 4-line plan on the slide and send them.
Lab — A Conversation That Plays Itself

Chain four lines: Cat (green flag) says a line, then broadcast [line 2] → Bear (when I receive [line 2]) replies, then broadcast [line 3] → Cat replies, then broadcast [line 4] → both glide off. Reference: labs/module-3/l3-1-conversation.sb3. Fast finishers: the Stage's when I receive [night] → switch backdrop to challenge.

Circulate for: only one script starts with the green flag; blocks on the wrong sprite; broadcast used where when I receive was meant (both are gold Events blocks); messages with near-identical names ("line2" vs "line 2").

Teach-It role-play — Story before code (6 min)
Kid card · Maya, age 6

Bouncy, excited, wants to spend ten minutes scrolling the sprite library. When asked "what does the character say?" she shrugs: "I don't know." Loves doing silly voices. Gets bored if the grown-up types for more than a minute.

Pairs: one plays Maya, one coaches through the 3-step story warm-up: Who? (two characters with names) → Where? (backdrop) → What happens? (act it out in voices). Swap once if time allows.

Let's be the characters first! You be the bear, I'll be the cat. What does the cat say? …Great, now let's make Scratch say exactly that.
Pick any two you like. We can come back to the library later. Who's our hero today?

Debrief (1 line): for ages 5–7, two lines each is plenty. The child picks the words, and the parent wires the broadcasts.

Watch-outs
  • Both sprites talk at once. This is the lesson's classic bug: both scripts start with when ⚑ clicked. Only line 1 starts on the flag. Every other line starts with when I receive.
  • "Where did my code go?" They added blocks with the Bear selected, then clicked the Cat. Reassure them: nothing is lost, each sprite has its own code area.
  • Trackpad drag struggles make broadcast dropdowns fiddly. Mice help. So does zooming the browser (Ctrl +) for anyone using reading glasses.
  • Sprite library rabbit hole. Adults do it too. Give a 60-second limit on choosing sprites.
  • Glide ends off-stage because of typos like x: 2000. Show them how to read the x/y under the stage.
Check — quiz

Answers: sprites take turns via broadcast and "when I receive"; smooth movement = glide _ secs to x/y; both talking at once = both start with "when ⚑ clicked" instead of "when I receive"; to change the scene, give the Stage when I receive [night] → switch backdrop to.

3.2

A Simple Game with Variables & Score

32 min
Objectives
  • Explain a variable and create one (score, "For all sprites")
  • Use set [score] to 0 and change [score] by 1; show the score on the stage
  • Combine loops, if, sensing, and operators into a playable game
  • Coach a child to design a game on paper and avoid the scope trap
Teaching sequence
  1. The whiteboard (3m). Stick a note on the wall: "SCORE: 0." Pretend to catch something, cross it out, write 1.
    That's a variable: a labeled box the computer remembers. set erases and writes a number. change adds to what's already there.
  2. Make the variable (2m). Variables (orange) → Make a Variable → score, keep For all sprites → OK. Point at the checkbox that shows it live on stage.
  3. The game plan (2m). Show the flowchart slide: apple starts at the top at a random x → falls → touching the cat? yes = +1 → back to top. Say it as a story before any block moves.
  4. Build the apple live (4m). Build it slowly and name each category as you use it (Motion, Control, Sensing, Operators, Variables). The bottom check is the green < block from Operators with the y position reporter (bottom of Motion) dropped into its left slot:
    when ⚑ clicked
    set score to 0
    forever
    go to x: pick random -200 to 200 y: 170
    repeat until touching Cat?
    change y by -8
    if y position < -170 then
    go to x: pick random -200 to 200 y: 170
    change score by 1
    Read it as a story: start at the top somewhere random, fall until the cat catches you, jump back to the top if you drop past the bottom, and when you're caught, add a point. Then do it all again, forever.
  5. Catcher preview (1m). Show the Cat script on the slide and let them build it themselves in the lab.
Lab — Catch the Apple

Add an Apple sprite, make score, build the apple script above, and give the Cat when ⚑ clicked → forever → go to x: (mouse x) y: -140. Play it. Save it (File → Save to your computer). Reference: labs/module-3/l3-2-catch-the-apple.sb3. Fast finishers: the 30-second time left timer challenge.

Circulate for: change score by 1 placed below the repeat-until's C-mouth (not inside it); touching dropdown set to Cat, not "mouse-pointer"; set score to 0 before the forever loop; mouse x (Sensing), not typed-in text; the bottom check is y position < -170, not touching edge?.

Teach-It role-play — Design first, and the scope trap (5 min)
Kid card · Theo, age 10

Confident, talks fast, has played a lot of games. Announces he wants to make "Minecraft but with dragons, and fifty levels, and online." Gets impatient with paper: "Can we just start?"

The coach walks Theo through the one-page design (Goal · Controls · Scoring · Lose condition) and steers him to one working mechanic, without saying "no."

Before we code, tell me your game like you're explaining it to a friend. How do you play? How do you win? Let's write those down. Those are our to-do list.
Dragons are awesome. Let's put fifty levels on the "someday" list and make catching one thing perfect first.

Debrief: a finished tiny game beats an abandoned huge one, for the child's motivation and the parent's.

Watch-outs
  • This lesson feels hard, so say so. Four categories plus a variable is a real step up. Adults compare themselves to the fast finisher at the next table. Tell them the lesson's growth-mindset point: "Big projects feel hard for everyone. Get one piece working, then the next."
  • Nesting mistakes. Dropping a block into the wrong C-mouth is the #1 error. Teach them to watch for the white "landing shadow" before releasing the mouse.
  • Score jumps by many at once: the apple is still touching the cat for several frames. The go to the top at the start of the next loop fixes it. Check that it's there.
  • "Why not touching edge?" Someone will swap it in for the bottom check, because it sounds right. The apple starts at y: 170, where it is already touching the top edge, so it's sent back to the top every frame and never falls. y position < -170 means "near the bottom" and nothing else. Don't argue it now. Park it, because it's your live debugging demo in 3.3.
  • Score never goes up: the touching block names the wrong sprite, or the apple never reaches the cat (check the cat's y is −140 and the apple's bottom check is −170, below it).
  • Screen-time guilt sometimes surfaces here ("my kid already plays too many games"). Reframe: making a game is creating, not consuming. Then move on. Don't let it take over the lab.
  • Unsaved work. This game is the basis for the Bug Hunt and Module 4. Make everyone save before the role-play.
Check — quiz

Answers: a variable is a named box that stores a value the program can change; add a point with change score by 1; set score to 0 goes right after the green flag, before the game loop; to see the score on the stage, tick the checkbox next to the variable.

3.3

Debugging & Remixing

30 min
Objectives
  • Apply the 4-step method: Watch → Predict → Change ONE thing → Test
  • Recognize the usual-suspect Scratch bugs and their fixes
  • Use See Inside on a shared project; explain remixing and its etiquette
  • Coach a frustrated child through a bug without taking over the mouse
Teaching sequence
  1. The mindset (2m).
    The computer isn't wrong and it isn't being mean. It's doing exactly what the blocks say. Debugging is the detective game of finding the gap between what you said and what you meant.
    Swap "It's broken, I failed" for "Interesting, let's find out why."
  2. The 4-step loop (3m). Show the slide. Stress step 3: change only one thing. Then name Scratch's helpers: click a single block to run it, tick a variable's checkbox to watch it, add a temporary say (score), slow things down with wait. Demo the rubber duck: explain a script to the stuffed animal and "find" a bug mid-sentence.
  3. Live bug: "Why not touching edge?" (included in the 3m above, or take 1m from See Inside). In your 3.2 game, swap the bottom check for if touching edge? and run it, thinking aloud through the four steps. Watch: the apple is frozen at the top. Predict: "It's being sent back to the top, so the if must be true right away. Is the apple touching an edge at y: 170?" (Yes, the top one.) Change one thing: put y position < -170 back. Test: it falls.
    The block did exactly what I told it: "touching any edge." I meant "the bottom." That gap between what I said and what I meant is the bug.
  4. Usual suspects + See Inside (3m). Walk the table on the slide quickly (it's in the workbook). Open any shared project on scratch.mit.edu → See Inside. Mention that Remix needs a signed-in account and that Scratch credits the original creator automatically.
  5. Bug Hunt launch. Form debugging-buddy pairs (below) and hand out 4-step cards. Say there are four bugs, but not what they are.
Lab — The Bug Hunt (17 min)

Pairs open labs/module-3/l3-3-bug-hunt-starter.sb3 (File → Load from your computer). It is the 3.2 catch game with four planted bugs. For each bug they write the symptom, their prediction, and the one change they made in the workbook's Bug Hall of Fame, then test. Solution: labs/module-3/l3-2-catch-the-apple.sb3.

Circulate for: pairs changing several blocks at once (stop them and ask "which one change are you testing?"); navigators grabbing the mouse; pairs who "fixed" a bug by rebuilding the whole script (fine, but ask them to name the one block that was wrong).

Debugging-buddy pair format
  • Driver: hands on the mouse. Only the driver touches the computer.
  • Navigator: holds the 4-step card and the workbook. Asks the "ask, don't fix" questions: What did you expect? What happened instead? Which block do you think is responsible? What's one thing we could change to test that? Writes the Bug Hall of Fame entry.
  • Swap roles after every bug, so each person drives twice and navigates twice.
  • One change, then test. If a change didn't help, undo it (Ctrl/Cmd+Z or drag it back) before trying the next idea.
  • This is a rehearsal of home: the navigator is practising being the parent who asks instead of grabbing.
The four planted bugs & hint ladder

Give hints only when a pair asks, one rung at a time, and wait about 2 minutes between rungs. Suggest they hunt in this order (easiest to see first): 1 → 3 → 4 → 2.

BugHint 1 · WatchHint 2 · PredictHint 3 · Nearly there
1 Cat drifts strangely"Move the mouse only left and right. What does the cat do? Now only up and down?""The cat's movement lives in the Cat's script. Which block decides where it goes?""Look at the round reporter inside go to x:. Is that the mouse's left–right number?"
2 Score carries over"Play a game, stop, then press the green flag again. What number does the score start at?""Something should wipe the whiteboard at the start of each game. Can you find it?""The Apple needs set score to 0 right after the green flag, before forever."
3 Apple never falls"Watch the apple. Is it moving? Tick its y position checkbox. Which way is the number going?""Only one block in the Apple's script moves it up or down. Find it.""Bigger y means up. Look at the number in change y by. Which sign do you need to fall?"
4 Score races while falling"Watch the score while one apple is still falling. When does it go up?""The +1 is running many times. Which loop is it inside?""change score by 1 should run once, after the apple is caught. Where is it sitting?"

With bug 4 still planted, the score races up even while bug 3 keeps the apple stuck at the top, so pairs often blame the wrong block. That's the point of changing one thing at a time. If a pair "fixes" things by swapping in touching edge?, the apple freezes again. Point them back to your live demo. Full fixes with drawn scripts are in the answer key.

Teach-It role-play — Ask, don't fix (5 min)
Kid card · Priya, age 9

Tired after school. Her game "doesn't work" and she has tried the same thing three times. Voice rising: "I'm bad at this!" Keeps pushing the mouse toward the grown-up: "YOU do it."

Same pairs, fresh roles. The coach keeps their hands in their lap and uses the rubber duck, the four questions, and (if needed) a break.

Walk me through it like I know nothing. What should this block do? …And what did it actually do?
The code has a bug; you're a coder who's finding it. Remember the one you squashed last week?
Let's let our brains rest. Coders do this all the time. We'll come back with fresh eyes.

Debrief: "Who felt the urge to grab the mouse?" (Every hand goes up.) The biggest parent mistake is fixing it yourself. That ends the frustration and the learning at the same time.

Watch-outs
  • Fear of breaking it. Some adults won't touch the starter file. Say plainly: "You can't break this. The original is on the drive, and you can reload it any time."
  • Shotgun debugging. Pairs change five blocks and "it works now." Praise the result, then ask which change mattered. They should be able to name it.
  • Loading the wrong file. Someone opens their own 3.2 game, finds no bugs, and feels clever. Check the title bar says bug-hunt-starter.
  • Remix = cheating? Parents worry about this. Everything shared on Scratch may be remixed, and credit is automatic. The line to teach is honesty: change something meaningful and keep the credit.
  • Home-device tech support ("my kid's Chromebook won't…"). Park it on a sticky note for after class.
Check — quiz

Answers: golden rule = change one thing at a time, then test; See Inside opens the project's code to explore how it was made; melting-down child = have them explain it aloud, or take a short break; flag clicked and nothing happens = the code is on the wrong sprite.

Closing the Session

S3 wrap-up (10 min)

Five minutes of silent journaling (the prompts are in the workbook), then ask two or three pairs to read one Bug Hall of Fame entry aloud and cheer each squashed bug. Recap: broadcasts let sprites take turns → a variable keeps score → Watch, Predict, Change one thing, Test.

Try at home this week: quietly move one block in the catch game and let your child debug it (using the four questions, hands in your lap); open one shared project together with See Inside; save the game, because its ideas come back in the Module 4 capstone.

Preview S4: "Next time one apple becomes a whole sky of falling stars with clones, and you'll make your own blocks. Homework after S4 is a Game Design Card you fill in with your child for Family Build Night."
